# ADR-001：采用运行级协作账本

## 状态

已接受

## 日期

2026-07-26

## 背景

原工作台按固定顺序调用 Planner、Searcher、Reader、Writer、Critic、Red 和 Blue。虽然存在 DAG 和共享内存，但默认页面只能看到节点完成状态，无法证明下游 Agent 消费了哪个上游产物，也无法解释审查问题如何进入修订。

同时，直接把 Agent JSON 或模型 token 展示给普通用户并不能说明协作过程，只会暴露协议细节。用户真正需要看到的是交接内容、处理动作、审查依据和报告版本变化。

本次升级明确不解决真实数据来源问题，因此还必须防止确定性 `mock://` 来源被误认为可信引用。

## 决策

采用单次研究运行范围内的 `ResearchLedger`：

- Agent 发布只追加版本的 `Artifact`。
- 下游 Agent 通过工件 ID 和版本读取依赖，不能覆盖上游产物。
- 每次发送、接收和退回形成 `Handoff` 与处理状态。
- Writer 只消费批准的 Findings；Red 发布可定位问题；Blue 记录问题处理结果和新报告版本。
- Red/Blue 至少执行两轮，必要时执行第三轮。
- 后端保留结构化 JSON 和 SSE 契约，普通工作台只显示中文可读 DTO。
- Writer 初稿、Red/Blue 审查和最终报告分别流式展示；最终报告在引用投影完成后发布。
- 模拟来源可以用于确定性流程测试，但不得进入公开 References 或通过状态的引用校验。

账本随单次运行存在，不作为跨问题长期记忆或研究语料库。

## 备选方案

### 继续使用线性角色调用

实现简单，但只能证明执行顺序，不能证明工件依赖、消费回执和审查闭环，因此拒绝。

### 在页面展示完整 Agent JSON

便于开发调试，但普通用户无法理解，且容易把模型内部输出误认为正式报告，因此仅保留机器接口，不作为默认界面。

### 引入 LangGraph、MCP 或 A2A

这些框架和协议适合跨服务或远程 Agent，但当前项目已有 Python DAG，引入新运行时不能直接解决工件责任和用户可读性，首期不采用。

### 把模型生成内容当作备用 Evidence

无法形成可追溯来源，会破坏引用可信度，因此拒绝。没有真实 Evidence 时必须明确降级。

## 结果

正面影响：

- Agent 协作可以通过工件版本、交接和消费记录复核。
- Red/Blue 的价值可以通过具体问题和修改前后内容观察。
- 普通界面保持可读，API 仍保持结构化和兼容。
- mock 不再伪装成已验证来源。

代价与限制：

- 一次研究会产生更多账本事件和模型调用，多轮审查会增加时间与额度消耗。
- 账本提高了协作可解释性，但不会提高外部数据覆盖率。
- 没有真实来源时，系统只能提供演示性分析并标记“需复查”，不能生成可信 References。
